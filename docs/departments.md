# Отделы и оркестратор (`serve --home`)

**Русский** · [English](departments.en.md)

Режим, в котором вы пишете задачи обычным текстом, а дальше всё идёт само: оркестратор раскладывает сообщение на задачи по отделам, каждый отдел делает работу в свежих сессиях Claude и Codex по своим правилам, внутреннее принимает оркестратор, то, что уходит наружу, принимаете вы. Ответы приходят в Telegram по мере готовности.

Замысел и решения — в [specs/001-departments](../specs/001-departments/spec.md). Установка на сервер — в [vps.md](vps.md).

## Быстрый старт

```sh
agentsflow home init ~/home        # дом: настройки, оркестратор, общий отдел, git
agentsflow home check ~/home       # проверить после правок
agentsflow serve --home ~/home --telegram
```

Telegram настраивается переменными `AGENTSFLOW_TELEGRAM_TOKEN` и `AGENTSFLOW_TELEGRAM_USERS` (см. README, раздел Telegram). Дальше просто пишите боту:

> Сделай пост в канал про запуск Orca, проверь остатки по Байтаку и посмотри, что пишут про рынок AI-агентов.

## Дом

```
home/
  agentsflow.toml          настройки: параллельность, оркестратор, цены Codex, часовой пояс
  orchestrator/AGENTS.md   правила оркестратора
  departments/<id>/
    department.toml        состав, workflow, лимиты, расписания
    AGENTS.md              правила отдела — меняются только с вашего согласия
    memory/notes.md        память отдела — агенты пишут сами
    runs/<task>/           папка запуска: brief.md, result.md, artifacts/
  .agentsflow/             доска, журнал расходов, расписания, лог (не в git)
```

Дом — git-репозиторий: каждое добавленное правило, новый отдел и смена лимита — отдельный коммит, их можно откатить.

## Как идёт задача

1. **Разбор.** Ваше сообщение получает свежая сессия оркестратора. Она отвечает планом: какие задачи, в какие отделы, с каким риском, что спросить. Шлюз проверяет каждое действие и создаёт карточки.
2. **Вопросы.** Если без ответа будет угадывание, задача ждёт: в Telegram приходит карточка с вопросами и кнопкой «✍ Ответить».
3. **Новый отдел.** Если подходящего нет, оркестратор предлагает отдел: «✅ Создать отдел» или «В общий отдел».
4. **Запуск.** Отдел получает бриф (`runs/<task>/brief.md`): правила, выжимку памяти, задачу, ваши ответы, входные данные. Workflow отдела — обычно исполнитель → ревьюер → исправление — идёт до одобрения ревьюера или до предела кругов.
5. **Приёмка.** `internal` (отчёт, анализ, черновик для вас) принимает оркестратор: принять, вернуть один раз с замечанием, или отдать вам. `external` (пост, письмо, изменение в чужой системе) всегда приходит вам: «✅ Принять», «🔁 Ещё круг», «✍ Вернуть с замечанием».
6. **Застряла.** Ревью не пройдено, вышло время, кончился бюджет — задача останавливается и приходит сводка: что сделано, сколько потрачено, кнопки «Ещё круг» и «Закрыть».

## department.toml

```toml
id = "pr"                       # латиница, совпадает с именем папки
title = "Пиар"
description = "Посты, анонсы, тексты для соцсетей"   # по нему оркестратор выбирает отдел
default_risk = "external"       # internal | external; по умолчанию external
max_parallel = 1                # задач отдела одновременно

[limits]
task_usd = 3.0                  # бюджет одной задачи
month_usd = 30.0                # месячный лимит отдела (необязателен)
warn_ratio = 0.8                # предупредить при 80 % месячного лимита
timeout_mins = 60
max_loops = 2                   # кругов ревью
stall_mins = 10                 # сколько агенты могут молчать, пока запуск не сочтут зависшим
tool_stall_mins = 30            # то же, пока идёт долгая команда (сборка, тесты)
on_stall = "restart"            # restart | notify: один автоперезапуск шага или только спросить вас

[[agent]]                       # 1–4 агента, хотя бы один doer
id = "writer"
kind = "codex"                  # claude | codex
model = "gpt-6.1-terra"         # необязательно
effort = "medium"               # необязательно
roles = ["doer"]

[[agent]]
id = "critic"
kind = "claude"
model = "claude-sonnet-5-5"
effort = "medium"
roles = ["reviewer"]

[[agent]]                       # необязательно: мелкие задачи
id = "fast"
kind = "claude"
model = "claude-haiku-5-5"
effort = "high"
roles = ["small"]

[[agent]]                       # необязательно: кончился лимит Codex
id = "spare"
kind = "claude"
model = "claude-sonnet-5-5"
effort = "medium"
roles = ["fallback"]

[[step]]                        # тот же формат шагов, что у workflow
id = "do"
agent = "@doer"
prompt = "{brief}"

[[step]]
id = "review"
agent = "@reviewer"
prompt = "{brief}\n\nРезультат:\n{prev.output}\n\nТы только проверяешь, файлы не меняй. Возвращай только за ошибки по существу, мелочи перечисли. Если их нет, последней строкой напиши VERDICT: APPROVED."
until = "VERDICT: APPROVED"
otherwise = "fix"
next = "end"

[[step]]
id = "fix"
agent = "@doer"
prompt = "Замечания:\n{review.output}\n\nИсправь и обнови result.md."
next = "review"

[[schedule]]                    # необязательно, сколько угодно
cron = "0 9 * * mon-fri"        # минута час день месяц день-недели
task = "Сводка продаж Байтака за вчера"
title = "Утренняя сводка"
```

Ревьюер в шаблоне возвращает работу только за ошибки по существу (неверные факты, не сделана часть задачи, нарушено правило); мелочи он перечисляет и одобряет, а на повторной проверке не добавляет новых требований. Строгий ревьюер гоняет годный результат по кругу, пока не кончится бюджет.

Агент, у которого роль только `reviewer`, по умолчанию работает с `sandbox = "read-only"`: с правом записи он кладёт свою рецензию в `result.md` поверх результата исполнителя. У Codex это его песочница. У Claude песочницы нет, поэтому запрещает охрана: инструменты записи и команды, которые похожи на запись (`>`, `rm`, `mv`, `sed -i`, `git commit`…), отклоняются сразу, не спрашивая вас. Скрипт, который пишет файл сам, она не увидит. Нужна запись — у Codex укажите `sandbox = "workspace-write"` явно, а Claude дайте вторую роль.

Состав по умолчанию (шаблон нового отдела и общий отдел): код пишет Codex `gpt-6.1-terra` medium, проверяет Sonnet 5.5 medium, мелкие задачи делает Haiku 5.5 high, при лимите Codex пишет Sonnet 5.5 medium.

- **`small`.** Оркестратор помечает задачу мелкой (`"size":"small"`), и её делает этот агент один, без ревью. `external` мелким не бывает. Задача, которую вернули с замечанием, идёт уже всем отделом.
- **`fallback`.** Codex сообщил о лимите подписки: задача снова ставится в очередь, запасной агент заменяет исполнителя и продолжает с файлов в папке, вам приходит уведомление. Следующая задача снова пробует Codex. Другие ошибки Codex задачу останавливают как обычно.

Такие агенты не запускаются, пока не нужны. У Codex-исполнителя есть цена вопроса: без `[prices.codex]` его работа не считается в бюджете в долларах, а охрана не видит его действий (запись ограничивает песочница, чтение чужих папок запрещено только в брифе).

`home check` показывает ошибки всех отделов сразу и предупреждения: нет ревьюера, ревьюер той же модели, что исполнитель, режим bypass, `live` с автоперезапуском молчащего шага, отдел с `[source]`, чьи правила не говорят, что текст извне — данные, и `delivery = "pr"` в репозиторий с папкой `deploy/`.

## Наставник

Одна сильная модель держит замысел задачи: пишет исполнителю постановку и сама, в той же сессии, проверяет результат. Исполнители остаются теми, что записаны в отделе. Включается и выключается на «Сцене» (внизу слева), в боте командой `/mentor` или через `POST /api/mentor {"preset": "..."}`:

| Выбор | Модель | Усилие |
|---|---|---|
| `fable-medium` | `claude-fable-5-2` | medium |
| `fable-low` | `claude-fable-5-2` | low |
| `opus-high` | `claude-opus-5-5` | high |
| `off` | состав отдела как записан | |

- Наставником становится агент отдела с ролью `reviewer`: на время запуска ему подменяются модель и усилие. В отделе без такого агента добавляется ещё один, только на чтение.
- Если workflow не начинается с шага наставника, перед первым шагом встаёт его постановка, и исполнитель получает её вместе с брифом. Если проверки наставником нет, после последнего шага встают проверка и исправление, до `max_loops` кругов.
- Мелкие задачи (`small`) идут без наставника.
- Выбор хранится в `.agentsflow/mentor.json` и действует на запуски, начатые после него. Наставник тратит бюджет задачи (`task_usd`) наравне с остальными.

## Память и правила

- Агент, узнав полезное для следующих задач, дописывает это в `memory.md` в папке запуска. После запуска шлюз переносит запись в `memory/notes.md` с датой и номером задачи; хвост памяти попадает в каждый следующий бриф (`memory_digest_kb`).
- Постоянное правило агент предлагает в `rule.md`. Вам приходит карточка «📜 Добавить / Отклонить». Добавленное правило дописывается в `AGENTS.md` отдельным коммитом; отклонённое запоминается в `memory/rejected.md`, и его больше не предлагают.
- Оркестратор тоже предлагает правила (например, когда вы пишете «запомни: отчёты всегда в xlsx») — отделу или себе.
- `/rules` в боте: открытые предложения и последние правила с кнопкой «↩ Отменить» (`git revert`).

## Заказы между отделами

Если отделу нужен результат другого (пиару — цифры от аналитики), агент описывает заказ в `request.md`. Задача ждёт, оркестратор оформляет заказ задачей другого отдела, а когда она готова, задача-заказчик запускается снова с результатом заказа во входных данных. Ограничения: не больше двух уровней заказов, заказ не идёт в отдел выше по цепочке, бюджет заказа — остаток бюджета заказчика, расход заказа учитывается у заказчика.

## Вопросы отдела

Если без ваших ответов задачу не сделать, агент пишет вопросы в `questions.md`, по одному в строке. Запуск на этом заканчивается без ревью, задача ждёт, вам приходит карточка «✍ Ответить»; после ответа отдел запускается снова с ответами в брифе. С заказом другому отделу так же: после `request.md` ревью не идёт. Ответ «на свой вкус» отдел считает ответом и выбирает сам.

## Изоляция

Запуск отдела работает в своей папке и может читать свой отдел: правила, память, прошлые запуски. Папки других отделов, оркестратора и `.agentsflow` закрыты: такие обращения агента Claude охрана отклоняет сразу, не спрашивая вас. Результаты задач, от которых зависит запуск (и выполненные заказы), шлюз копирует в `inputs/<задача>/` его папки вместе с `artifacts/`. Codex охрана не видит, ему это сказано в брифе, а ревьюер Codex по умолчанию только читает.

## Расходы

Каждый ход записывается в `.agentsflow/ledger.jsonl` с токенами: Claude сообщает стоимость сам, Codex считается по токенам и ценам `[prices.codex."<модель>"]` в `agentsflow.toml` (без цены в долларах не учитывается, но его токены видны отдельной строкой «без цены»). Карточки задач, отделы на странице и `/spend` показывают доллары и токены: `$0.25 · 340k → 3k токенов` (вход → выход). Задача, превысившая бюджет, останавливается. Отдел, исчерпавший `month_usd`, останавливает запуски и держит очередь; при `warn_ratio` приходит предупреждение. `/spend` в боте показывает расходы за месяц и поднимает лимит на 50 %.

## Расписания

`[[schedule]]` в отделе ставит задачу в очередь по cron из пяти полей (`*`, списки, диапазоны, шаги `*/15`, имена `mon`/`jan`, `@daily`, `@weekly`, `@monthly`). Время — по `utc_offset` в `agentsflow.toml` (например `"+05:00"`). После перезапуска сервера срабатывание не повторяется, а пропущенное за время простоя выполняется один раз. `/schedules`: пауза, «⚡ Сейчас».

## Присмотр за запусками

Шлюз следит за тишиной идущего запуска: любое событие его агентов (мысль, сообщение, вызов инструмента и его результат) считается признаком жизни. Пока идёт инструмент (сборка, тесты), допустимая тишина дольше: `tool_stall_mins` вместо `stall_mins`. Запрос разрешения, который ждёт вас, тишиной не считается.

Когда запуск молчит дольше допустимого:

- **`on_stall = "restart"` (по умолчанию).** Шаг один раз перезапускается в свежей сессии, и агент получает записку: предыдущая сессия зависла, файлы в папке запуска остались, продолжай с этого места и не повторяй уже выполненные отправки, публикации и push. Вам приходит письмо «Шаг перезапущен». Если шаг уже сделал что-то наружу, автоперезапуска нет: повторить такое действие было бы хуже тишины. «Наружу» охрана считает всё, что не входит в короткий список известных локальных программ (чтение, сборка, тесты, правка файлов): `git push`, `gh`, `curl` и `wget` с записью, `npm publish`, `docker push`, `ssh`, письмо, сообщение, запись через коннектор. Незнакомая программа и команда внутри `bash -lc`, `$(...)` или скобок разбираются так же, а если разобрать нельзя, это тоже «наружу».
- **`on_stall = "notify"`, второй зависший круг того же шага или действие наружу.** В карточке задачи (страница и Telegram) стоит «молчит N мин» и три кнопки: «Подождать ещё» (ещё один срок тишины), «Перезапустить шаг», «Остановить».

Молчание сообщается один раз; любое новое событие агента снимает метку. Отделу с `live = true` автоперезапуск лучше выключить (`on_stall = "notify"`): `home check` об этом напомнит.

## События из репозитория

Отдел может сам заводить задачи по событиям GitHub. Шлюз ничего не слушает снаружи: раз в `poll_secs` секунд он спрашивает `gh` (не больше 60 вызовов в час на отдел), а каждое новое событие превращает в одну внутреннюю (`internal`) задачу.

```toml
[source]
repo = "owner/name"
events = ["ci_failure", "issue_label:agent", "pr_comment:/agent"]   # пусто: репозиторий нужен только для PR
branches = ["main"]            # ветки, чьи падения CI считаются
poll_secs = 120                # 30..=3600
own = true                     # ваш репозиторий: закрывающий комментарий уходит сразу
```

- `ci_failure` — упавший прогон CI на отслеживаемой ветке (прогоны pull request, в том числе из форков, не считаются); `issue_label:<метка>` — issue с этой меткой; `pr_comment:<префикс>` — комментарий к PR или issue, начинающийся с префикса, и только от владельца, участника или соавтора репозитория (комментарий постороннего задачи не создаёт).
- За один опрос появляется не больше трёх новых задач, остальные придут на следующих опросах. Каждый вызов `gh` ограничен 120 секундами: зависший вызов не останавливает шлюз.
- Первый опрос только запоминает уже существующее и задач не создаёт. Повторы отсекаются по ключам в `.agentsflow/sources.json`.
- Текст из issue, комментария и лога CI (вместе с заголовком) попадает в бриф между границами со случайной меткой и считается данными, не инструкциями. Название задачи шлюз составляет сам («Issue #7 в o/r»), чужой заголовок в него не идёт. Правила отдела должны это говорить (в шаблоне нового отдела строка уже есть, `home check` проверит у остальных).
- На карточке задачи видно, из какого события она появилась, и ссылка на него.

## Результат как pull request

```toml
worktree = true
repos = ["C:/Dev/sbx"]
delivery = "pr"                 # требует worktree, repos и [source] с repo
```

Агент только коммитит в своей копии репозитория. Шлюз забирает ветку `agentsflow/<задача>` в ваш репозиторий, пушит её оттуда без `--force` и открывает черновой pull request (`gh pr create --draft`); ссылка появляется в карточке и в итоге. Слияние и снятие пометки черновика остаются за вами. Переменные `GH_TOKEN` и `GITHUB_TOKEN` шлюза в окружение агентов не попадают, но сохранённый на машине вход (`gh auth login`) остаётся доступен любой команде агента: поэтому `git push` и `gh` у агента охрана считает действием наружу, а защитой служат ревью и ваш просмотр черновика, а не отсутствие доступа.

Правила выдачи:

- Ветка уходит сама только после ревью. Задачу, которую сделал мелкий агент один, шлюз не отдаёт: ветка остаётся в локальной копии, приходит письмо «PR не открыт».
- `delivery = "pr"` не принимается у отдела без агента с ролью `reviewer`.
- Ветка, где менялись файлы CI (`.github/`, `.gitlab-ci`, `Jenkinsfile`, `.circleci/` и подобные), сама не уходит: такой push запускает код с секретами репозитория, поэтому ветку смотрите и отправляете вы.
- Заголовок PR и комментарий очищены от `@имя`: никого не позовут.

Если задача появилась из issue или комментария, шлюз пишет туда закрывающий комментарий фиксированной формы: первая строка итога, ссылка на PR, расход; упоминания `@имя` обезврежены. В репозиториях с `own = true` комментарий уходит сразу, в чужих ждёт вашего «Опубликовать комментарий» (или «Не нужно») в карточке. Комментарий пишется один раз на задачу: второй круг после «Ещё круг» нового не добавляет, а «Не нужно» отменяет его насовсем.

## Сторож шлюза

`agentsflow watch --home DIR` — отдельный небольшой процесс, который смотрит на шлюз снаружи. Раз в `interval_secs` он спрашивает `GET /api/alive` (единственная ручка без токена; она отвечает только `{ok, version}`). Если шлюз молчит `misses` раз подряд, сторож пишет вам в Telegram напрямую, не через шлюз, а с `kill_hung = true` ещё и завершает зависший процесс, чтобы автозапуск поднял новый (не чаще раза в 5 минут и не больше трёх раз подряд; завершается только процесс `agentsflow`, слушающий порт). Когда шлюз снова отвечает, приходит «снова работает». Если Telegram в этот момент недоступен, сообщение не теряется: сторож повторяет его при каждом следующем взгляде (до часа, не больше 20 сообщений). Сторож читает только `agentsflow.toml`, поэтому сломанный `department.toml` его не останавливает. После перезапуска шлюз сам присылает, какие запуски прервались.

```toml
# agentsflow.toml
[watch]
alive_url = "http://127.0.0.1:7878/api/alive"   # только локальный адрес
interval_secs = 60
misses = 3
kill_hung = true
```

Сторожу нужны те же `AGENTSFLOW_TELEGRAM_TOKEN` и `AGENTSFLOW_TELEGRAM_USERS`. Проверка настройки без цикла: `agentsflow watch --home DIR --once`.

- **VPS.** `deploy/agentsflow-watch.service` (установка — в шапке файла), служба `agentsflow-watch` рядом с `agentsflow`.
- **Windows.** `deploy/watch.ps1` держит сторожа живым (как `autostart.ps1` шлюз) и запускает его из копии `agentsflow-watch.exe`, чтобы пересборка шлюза не упиралась в занятый файл. Задачу планировщика заводите один раз вручную:

  ```powershell
  $action = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument '-NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File "<путь к репозиторию>\deploy\watch.ps1"'
  Register-ScheduledTask -TaskName 'agentsflow-watch' -Action $action -Trigger (New-ScheduledTaskTrigger -AtLogOn)
  Start-ScheduledTask agentsflow-watch
  ```

### Файлы

Бот принимает документы, фото, аудио, видео и голосовые до 20 МБ (предел Telegram для ботов). Файлы ждут в `.agentsflow/inbox/`, а при запуске задачи копируются в `inputs/owner/` её папки; бриф называет их агенту. Оркестратор передаёт файлы всем задачам из сообщения. Если подписи нет, бот спросит, что сделать, и через 30 минут без ответа уберёт файлы.

Читалка показывает `result.md` и текстовые файлы из `artifacts/` постранично прямо в чате: Markdown превращается в обычное оформление, широкие таблицы в карточки. Двоичные файлы и файлы больше 1 МБ приходят документом. Telegram принимает от бота до 50 МБ; для файла больше бот называет путь на диске. Символические ссылки бот не читает. Когда оркестратор сам принял задачу, бот присылает её итог с кнопками чтения.

|---|---|

| `POST /api/work` `{text, department, title?, risk?, depends_on?, budget_usd?}` | задача в отдел напрямую |

| `POST /api/tasks/{id}/supervise/{wait\|restart\|stop\|publish\|drop}` | молчащий запуск: подождать, перезапустить шаг, остановить; закрывающий комментарий: опубликовать, не нужно; 409, если запуск уже не идёт |

## Что стоит знать

- Свежая сессия Claude — это около 95 тысяч токенов контекста на старте; разбор сообщения оркестратором на Sonnet стоит порядка $0.08, короткая задача отдела — $0.2–0.4.
- Codex на подписке не сообщает стоимость: без `[prices.codex]` его расход не попадает в лимиты.
- Месяц в журнале расходов считается по UTC.
- Лог шлюза (`.agentsflow/server.log` и stderr, то есть journalctl на VPS): создание задач, каждая смена состояния с расходом, запуски отделов, решения и ошибки оркестратора, остановка сервера и паники. Время в логе — UTC.
- Страница в этом режиме открывается на «Сцене». Слева «Ждёт вас» и отделы с их задачами. В середине агенты выбранной задачи рядом, у каждого своя лента: бриф или то, что передал коллега, «Думал N с» с его мыслями, «Работал · N команд» с командами и их итогом, правки файлов карточками, ответы и вердикт ревьюера. Над агентами полоса шагов (исполнение, ревью, «вернул», исправление, приёмка), справа карточка задачи: отдел, кто принимает, бюджет, время, вопросы, результат, файлы и действия (принять, ещё круг, вернуть с запиской, остановить). На телефоне агенты переключаются вкладками.
- Писать агенту можно прямо в его ленте, пока задача идёт. Если он занят, записка дойдёт сразу после его текущего хода: агент получит её отдельным ходом и ответит заново с её учётом. Если он ждёт своей очереди, записка уйдёт вместе с его следующим шагом. Записка, до которой очередь не дошла (задача кончилась или сервер перезапустился), помечается «не дошло».
- «Доска» показывает задачи колонками «В очереди», «В работе», «Ждёт вас», «Готово». Перетащить идущую задачу в очередь — остановить её и вернуть с запиской; результат в «Готово» — принять (для внешней задачи страница переспросит); готовую или застрявшую в очередь — новый круг с запиской. Прямые ссылки: `#task=<id>`, `#board`, `#new`. Готовая задача открывается на вкладке «Итог», как чат: сверху запрос пузырём справа с вашими файлами, ниже ответ отдела с таблицами, под ним файлы карточками (итог скачивается под названием задачи) и кнопки «копировать», «скачать», «как работали». Готовый итог, который вы ещё не открывали, подсвечен слева и на доске меткой «новое»; метка снимается, когда задача пробыла открытой пару секунд (запоминает браузер).
- Задачи, которые оркестратор заводит на приёмке результата, получают файлы принятой задачи: вложения хозяина, `result.md` и `artifacts/` запуска (без логов браузера). Исполнитель найдёт их во входных данных, оркестратор видит их список в приёмке. Прежняя вкладка «Отделы» с правилами и расписаниями открывается кнопкой с квадратами внизу слева.

## Сайты с входом

Отдел может входить на сайты, например в кабинет Kaspi или 1С:Фреш:

1. Скопируй `deploy/sites.example.toml` в `<дом>/.agentsflow/sites.toml` и сам впиши логины и пароли. Заведи для этого отдельные учётные записи только на чтение: вошедший агент может нажать всё, что разрешено учётной записи.
2. Добавь в начало `department.toml` строку `sites = ["kaspi", "onec"]`. У такого отдела `max_parallel = 1`, исполнитель — Claude, защита включена у всех агентов.
3. `agentsflow home check` покажет, чего не хватает.

Как это работает:

- Исполнитель получает инструмент `site_login` и инструменты браузера `browser` (Playwright MCP). Ревьюер браузера не получает.
- `site_login` читает файл сам, заполняет форму в Chrome отдела и возвращает агенту только итог. Пароль не попадает ни в модель, ни в `events.jsonl`.
- Папку `.agentsflow` защита закрывает для отделов. Защита судит по тексту команды, поэтому агента, который специально её обходит, она может и не остановить.
- Сайт просит код: агент спрашивает его у хозяина обычным вопросом, Chrome ждёт открытым, следующий запуск вводит код в ту же форму.
- Капчу никто не обходит: агент сообщает о ней хозяину. При неверном пароле агент не пробует снова, чтобы не заблокировать учётную запись.
- Профиль браузера лежит в `<дом>/.agentsflow/browser/<отдел>`. Нужны Chrome и Node.js (`npx`).
