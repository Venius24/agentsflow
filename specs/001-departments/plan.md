# 001 · Отделы и оркестратор — план реализации

Что строим — [spec.md](spec.md). Здесь — как это ложится на нынешний код.

## 1. Что есть сейчас и что меняется

| Сейчас | Становится |
|---|---|
| `team.toml`: 1–6 агентов, у каждого один вечный процесс CLI, запущенный при старте сервера (`runtime.rs`). | Агенты принадлежат отделу и живут один запуск: процесс поднимается под задачу и гасится после неё. |
| Одна рабочая папка `--cwd` на всех. | Домашняя папка `--home`; у каждого запуска своя `departments/<id>/runs/<task>/`. |
| `workflow::Manager`: одновременно один workflow, общий флаг `hub.admission()`. | `RunManager`: очередь и до `max_parallel_runs` запусков, у отдела свой `max_parallel`. Блокировка — на запуск, а не на хаб. |
| «Оркестратор» — это хозяин за страницей. | Оркестратор — ИИ-сессия на событие с MCP-инструментами доски; хозяин — «хозяин». |
| Доска: статусы backlog…archived, исполнитель — агент. | Задача получает отдел, риск, зависимости, родителя, запуски, расходы, вопросы и ответы, результат. |
| Стоимость считается (Claude), но ни на что не влияет. | Учёт по запуску/задаче/отделу/месяцу и остановка по лимитам. |
| Почта между агентами. | Остаётся внутри запуска для общения агентов отдела; между отделами — заказы через оркестратора. |

Переиспользуем без изменений по сути: формат событий и SSE, адаптеры Claude/Codex, actor-модель хаба (`hub::spawn_guarded`), движок шагов `workflow::execute` (`until` / `otherwise` / `max_loops` / `next`), guard и режимы доступа, журнал, экспорт, Telegram-каркас (экраны, кнопки, белый список).

Старый режим `serve --team` не трогаем, пока новый режим `serve --home` не закроет этапы 1–2; удаление старого — отдельное решение хозяина.

## 2. Домашняя папка

```
<home>/                          git-репозиторий (FR-42)
  agentsflow.toml                глобальные настройки
  orchestrator/
    AGENTS.md                    правила оркестратора (тоже через одобрение)
  departments/
    general/                     общий отдел, создаётся при init
    pr/
      department.toml
      AGENTS.md                  правила отдела
      memory/
        notes.md                 заметки агентов
        rejected.md              отклонённые правила
        proposals/<id>.md        ждут решения хозяина
      runs/<task-id>/            в .gitignore
        brief.md                 что получил запуск
        result.md                итог
        artifacts/               файлы результата
  .agentsflow/                   в .gitignore: events.jsonl, ledger.jsonl, server.log
```

`agentsflow.toml`:

```toml
max_parallel_runs = 3

[orchestrator]
kind = "claude"
model = "claude-sonnet-5-5"
effort = "medium"

# Пример: имя модели и цены — заглушки, перед запуском сверить с прайсом.
[prices.codex."<модель codex>"]     # долларов за миллион токенов
input = 0.0
cached_input = 0.0

```

`department.toml` (состав — поля нынешнего `[[agent]]`, шаги — нынешний `[[step]]`):

```toml
id = "pr"
title = "Пиар и внешние коммуникации"
description = "Посты, анонсы, письма партнёрам, работа с упоминаниями. Готовит черновики; наружу отправляет только после одобрения хозяина."
max_parallel = 1
default_risk = "external"

[limits]
task_usd = 3.0
month_usd = 50.0
timeout_mins = 60
max_loops = 2

[[agent]]
id = "writer"
kind = "claude"
model = "claude-sonnet-5-5"
mode = "smart"
roles = ["doer"]

[[agent]]
id = "critic"
kind = "codex"
roles = ["reviewer"]

[[step]]
id = "do"
agent = "@doer"
prompt = "{brief}"

[[step]]
id = "review"
agent = "@reviewer"
prompt = "{brief}\n\nРезультат исполнителя:\n{prev.output}\n\nПроверь по правилам отдела. Если всё верно — последней строкой VERDICT: APPROVED, иначе перечисли замечания."
until = "VERDICT: APPROVED"
otherwise = "fix"
next = "end"

[[step]]
id = "fix"
agent = "@doer"
prompt = "Замечания ревьюера:\n{review.output}\n\nИсправь."
next = "review"

[[schedule]]
cron = "0 9 * * MON"
task = "Еженедельная сводка упоминаний Orca"
```

`max_loops` шага по умолчанию берётся из `[limits]`.

## 3. Компоненты

Все новые модули — в `crates/gateway/src/`.

### 3.1 `home.rs`
Загрузка и проверка домашней папки: `agentsflow.toml`, список отделов, правила оркестратора. `agentsflow home init <DIR>` создаёт скелет с отделом `general` и стартовыми правилами оркестратора, делает `git init` и первый коммит. `agentsflow home check` — как `team check`: таблица отделов, составов, лимитов, ошибки. Коммиты изменений правил и отделов — вызовом `git` (как `doctor` уже вызывает внешние программы).

### 3.2 `department.rs`
`Department { id, title, description, max_parallel, default_risk, limits, members: Vec<team::Member>, workflow: workflow::Spec, schedules }`. Разбор переиспользует `team::Member` и разбор шагов `workflow::Spec::parse`; проверки — те же (ровно один лидер не нужен, роли `@doer` / `@reviewer` обязательны, 1–3 агента).

### 3.3 Бриф (`brief.rs`)
Агенту не доверяем самостоятельный поиск `CLAUDE.md` / `AGENTS.md` (у Claude и Codex разные правила поиска). Шлюз сам собирает `brief.md` и подставляет его в плейсхолдер `{brief}`:

```
# Правила отдела                ← AGENTS.md
# Память отдела (выжимка)       ← хвост memory/notes.md до memory_digest_kb
# Задача #<id>                  ← текст задачи
# Уточнения хозяина             ← вопросы и ответы
# Входные данные                ← пути к result.md зависимостей / родителя
# Как сдать работу              ← писать в artifacts/, итог в result.md, инструменты remember / propose_rule / ask_owner
```

`CLAUDE.md` в отделах не создаём, чтобы правила не попадали в контекст дважды.

### 3.4 Запуски (`runs.rs`)
`RunManager` заменяет однопоточный `workflow::Manager` в новом режиме:

- очередь задач в статусе `queued`; отбор с учётом `max_parallel_runs`, `max_parallel` отдела, зависимостей и бюджета;
- на запуск: создать `runs/<task>/`, записать `brief.md`, поднять акторы членов отдела через `hub::spawn_guarded` с `cwd = runs/<task>/`, `session = <run-id>`, `agent = "<dept>:<member>"`;
- вызвать `workflow::execute` с картой этих акторов (сигнатура уже принимает `Agents`), затем `shutdown` всех;
- остановка: `stop` (кнопка хозяина), `timeout_mins`, превышение `task_usd` (проверяется на каждом `done` с расходом), `max_loops` → статус `stuck` с причиной;
- итог: `result.md` (если агент не записал — последнее сообщение последнего шага), выжимка в карточку, событие для оркестратора.

Изменения в существующем коде:
- `hub.admission()` — глобальный флаг «идёт workflow» — заменяется блокировкой на запуск; старый режим продолжает пользоваться своим флагом.
- Проверка `AgentId` разрешает `:` для агентов отделов.
- `Envelope.session` уже есть — по нему лента группируется по запускам.

### 3.5 Задачи (расширение `hub.rs`)
К `TaskSnapshot` добавляются: `department`, `risk`, `parent`, `depends_on`, `runs: Vec<RunRef>`, `questions: Vec<Qa>`, `cost_usd`, `result_summary`, `result_path`, `stuck_reason`. Новые статусы: `waiting` (ждёт хозяина) и `stuck` (застряла); `queued` и `running` отображаются на нынешние `todo` и `in_progress`, `review` = ждёт приёмки. Снимки в журнале по-прежнему восстанавливают доску; старые снимки без новых полей читаются (`#[serde(default)]`).

### 3.6 Оркестратор (`orchestrator.rs`)
Событийный цикл. Триггеры: сообщение хозяина, ответ хозяина на вопрос, запуск завершён/застрял, заказ от отдела, решение хозяина по предложенному отделу. Триггеры складываются в очередь и сливаются; одновременно работает один вызов оркестратора.

Вызов = новая сессия Claude в `<home>/orchestrator/` с промптом: правила оркестратора, каталог отделов (id, title, description, загрузка, остаток бюджета), открытые задачи, сам триггер.

**Решение на этапе 2:** оркестратор не вызывает MCP-инструменты, а отвечает одним JSON-планом `{message, actions[]}`. Шлюз разбирает план, проверяет и применяет каждое действие сам. Причины: одна сессия без инструментов дешевле и быстрее, весь ход виден и проверяется целиком, нет второго токена и процесса MCP. Действия те же, что в таблице ниже (`create_task`, `propose_department` с задачами, `ask_owner`, `accept`, `return_task`, `send_to_owner`); чтение заменено тем, что каталог и открытые задачи уже в промпте, `notify_owner` — полем `message`. Ошибка сессии или разбора: сообщение хозяина возвращается ему с причиной, результат на приёмке уходит хозяину. MCP остаётся для агентов отделов (этапы 4–5).

| Инструмент | Что делает |
|---|---|
| `list_departments`, `list_tasks`, `get_task` | Чтение. |
| `create_task {title, text, department, risk, depends_on?, budget_usd?}` | Задача в очередь. |
| `ask_owner {task, questions[]}` | Задача → `waiting`, вопросы — хозяину одним сообщением. |
| `propose_department {id, title, description, agents, workflow, rules}` | Черновик отдела хозяину на «создать / править / в общий». |
| `accept {task, note}` | Только `internal`: задача → `done`. |
| `return_task {task, reason}` | Вернуть в отдел с замечанием (оно попадёт в бриф), не более одного раза; второй возврат отдаёт результат хозяину. |
| `send_to_owner {task, summary}` | `external` и итоги — хозяину на приёмку. |
| `notify_owner {text}` | Короткое сообщение хозяину. |

Шлюз проверяет каждое действие: `accept` для `external` отклоняется, пустой `ask_owner` отклоняется, несуществующий отдел — ошибка инструмента.

### 3.7 MCP-сервер
Нынешний `mail_mcp.rs` (`agentsflow mail-mcp --as <id>`) расширяется до `agentsflow mcp --as <id> --role orchestrator|member` с личным токеном на роль. Инструменты агента отдела:

| Инструмент | Что делает |
|---|---|
| `remember {note}` | Дописать в `memory/notes.md` (с датой и задачей). |
| `propose_rule {text, why}` | Предложение правила хозяину. |
| `ask_owner {question}` | Вопрос хозяину; ход агента ждёт ответа (как почтовый шаг ждёт письма). |
| `request_department {text, department?}` | Заказ подзадачи (этап 5). |
| `report_progress {progress, note}` | Прогресс в карточке (нынешний `update_task`). |
| `send_mail`, `check_inbox` | Как сейчас, внутри запуска. |

### 3.8 Деньги (`ledger.rs`)
`.agentsflow/ledger.jsonl`: запись на каждый ход с расходом `{ts, month, department, task, run, agent, kind, model, input, cached_input, output, usd, usd_source: "cli"|"price"}`. Claude — `total_cost_usd` из CLI, Codex — токены × цена из `[prices.codex]`; модели без цены — ошибка `home check`, а не тихий ноль. Агрегаты для доски, страницы и бота строятся при старте и обновляются инкрементально. Лимиты: `task_usd` (запуск останавливается), `month_usd` (отдел не берёт новые задачи, текущий запуск останавливается после текущего хода).

### 3.9 Память и правила
`remember` и `propose_rule` — файлы в `memory/`. **Решение на этапе 4:** агенты не вызывают инструменты, а оставляют в папке запуска `memory.md` (заметки) и `rule.md` (одно правило). После запуска шлюз дописывает заметки в `memory/notes.md` под датой и задачей, а правило кладёт в `memory/proposals/<task>.md` и присылает хозяину карточку. Так одинаково работают Claude и Codex, и не нужен MCP. Отклонённые правила копятся в `memory/rejected.md` и попадают в бриф, чтобы их не предлагали снова. Оркестратор предлагает правила действием `propose_rule` (для отдела или для себя). Одобрение правила: дописать в `AGENTS.md` под датой, удалить предложение, `git commit -m "rule(<dept>): …"`. Откат — `git revert` кнопкой «отменить» у последних правил (страница и бот). cass-memory — отдельная проба на этапе 4: годится ли хранить память по отделам и отдавать `cm context` в бриф; до решения — простые файлы.

### 3.10 Telegram
- Любой текст хозяина без команды уходит оркестратору (С1). Нынешняя «Написать агенту» остаётся командой.
- Ответ хозяина reply'ем на сообщение с вопросами — ответ на эти вопросы.
- Карточки с кнопками: предложение отдела, предложение правила, приёмка `external`, застряло (ещё круг / переформулировать / закрыть), бюджет кончился (поднять лимит / не надо).
- Экраны: «Доска» по отделам, «Отделы» (состав, загрузка, бюджет), «Расходы» (месяц по отделам).

### 3.11 Веб
Доска с группировкой по отделам; карточка задачи с запусками, лентой агентов запуска (по `session`), результатом и расходом; страница отделов; расходы. Колонки агентов старого режима остаются для `--team`. Паритет с ботом — по таблице в README, она дополняется.

### 3.12 Расписание (`schedule.rs`)
Тик раз в 30 секунд, разбор cron-выражения отдела (крейт `croner`), время последнего срабатывания — в журнале. Созданная задача идёт сразу в свой отдел, минуя маршрутизацию оркестратора.

### 3.13 Перезапуск
Незавершённые запуски при старте → `stuck` с причиной «сервер перезапущен» и кнопкой «запустить заново». Незаданные вопросы и ждущие решения карточки восстанавливаются из журнала.

### 3.14 VPS
Linux, `systemd`-служба `agentsflow serve --home /srv/agentsflow --telegram`. `claude` и `codex` авторизуются на сервере один раз. Страница слушает только `127.0.0.1`, доступ — `ssh -L` или Tailscale. Пример юнита и инструкция — в README. CI уже проверяет Linux.

## 4. Решения, принятые в плане

| Вопрос | Решение | Почему |
|---|---|---|
| Как агент узнаёт правила | Шлюз вставляет их в бриф | Одинаково для Claude и Codex, видно в `brief.md`, не зависит от правил поиска файлов CLI. |
| Состояние оркестратора | Только доска и каталог отделов | Принцип изоляции; сбой одной сессии ничего не ломает. |
| Отделы договариваются | Через оркестратора, глубина ≤ 2 | Выглядит как прямой заказ, но цепочки и деньги под контролем. |
| Ревьюер | По умолчанию другая модель, чем исполнитель | Ревью той же моделью слабее. |
| Память | Файлы в отделе; cass-memory — проба на этапе 4 | Его автоматическое повышение заметок в правила противоречит принципу 4, и хранилище по умолчанию общее. |
| Старый режим | Живёт параллельно до конца этапа 2 | Не ломаем рабочий инструмент, пока новый не готов. |

## 5. Открытые вопросы

1. Модель оркестратора по умолчанию: `claude-sonnet-5-5` (дешевле) или Opus (точнее раскладывает). Сейчас — Sonnet, меняется в `agentsflow.toml`.
2. Цены Codex для подписки ChatGPT не отражают реальных денег: лимиты по долларам для Codex на подписке — условные. Возможно, понадобится лимит в токенах.
3. Нужен ли отделу доступ на чтение к результатам других отделов без заказа (например, «последний отчёт по Байтаку»). Пока — только через зависимости и заказы.
