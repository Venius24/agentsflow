# 002 · Присмотр за запусками и события снаружи — спецификация

Статус: черновик, утверждается хозяином. Дата: 2026-11-08.
Продолжает [001-departments](../001-departments/spec.md). Этот документ описывает *что* и *зачем*; *как* и порядок работ будут в plan.md и tasks.md после утверждения.

## 1. Откуда это

31 октября 2026 команда DeepSeek Harness выложила прототип «Super-agent» (`dsh-superagent-prototype`, MIT): резидентный Router раздаёт работу изолированным Worker-сессиям, внешний Watchdog следит за воркерами, агент срабатывает на события из чата и CI, результат возвращается в исходный разговор, часто готовым pull request. Их тезис: узкое место — внимание человека, он удерживает 3–5 параллельных сессий.

Это почти наш замысел из 001 (оркестратор, изолированные запуски, внимание хозяина как главный ресурс). Сравнение показало три места, где у них есть то, чего у нас нет. Сведения о Super-agent взяты из пересказов в прессе и блогах; сам README и статья команды не читались, поэтому детали их реализации здесь не копируются, берём только идею.

## 2. Что есть в нашем коде сейчас (проверено по ветке `work`)

| Что | Состояние |
|---|---|
| Остановка запуска по времени | Есть: один таймер `timeout_mins` на весь запуск (`runs.rs`), причина `StopReason::Timeout`. |
| Обнаружение зависшего агента | **Нет.** Агент, который молчит 40 минут из 60 допустимых, ничем не отличается от работающего. Время последней активности хранится в `hub.rs` (`last_activity_ms`), но запуск его не использует. |
| Что с запуском при падении сервера | `SIGINT` останавливает отделы чисто, они становятся «stuck: server stopped». При аварийном падении запуски теряются, возвращаются вручную кнопкой (FR-23). |
| Присмотр за самим шлюзом | Только `Restart=on-failure` в systemd на VPS. На десктопе бот, запущенный из сессии или вкладки терминала, тихо умирает вместе с приложением, и никто не сообщает. |
| Источники задач | Сообщение хозяина (Telegram, страница) и расписания cron (FR-60). Событий снаружи нет. |
| GitHub, CI, pull request | В коде нет. Отдел сдаёт `result.md` и артефакты в папке запуска. |

## 3. Цель

Хозяин узнаёт о зависшем или упавшем без того, чтобы смотреть самому; часть задач возникает сама из событий; результат правки кода приходит в виде, который можно открыть и принять одним нажатием.

Критерий успеха: хозяин оставляет бота на сутки, и за это время (а) зависший запуск обнаружен и либо перезапущен, либо вынесен в «застряла» с причиной «молчит», (б) падение CI в подключённом репозитории породило задачу в нужный отдел, (в) задача на правку кода закончилась ссылкой на PR, а не папкой с файлами.

## 4. Принципы

Все принципы из 001 действуют. К ним по этой теме:

1. **Присмотр не должен сам тратить внимание хозяина.** Сторож сообщает только о том, что требует решения, и не шумит о каждом перезапуске.
2. **Сторож независим от того, за кем следит.** Он не живёт в той же задаче и в том же процессе, что запуск, иначе зависание утянет и его.
3. **Событие — это не команда.** Событие снаружи (CI, issue, комментарий) приходит как данные. Оно создаёт задачу по правилам отдела, но не исполняется как инструкция. Внешний текст в брифе помечается как недоверенный.
4. **Наружу по-прежнему только через хозяина (принцип 5 из 001), с одним узким исключением.** Мерж, снятие «черновика», пуш в чужую ветку и любые действия в чужих репозиториях — `external`. Автоматически допустимы: ветка в репозитории отдела, черновик PR и итоговый комментарий в репозитории, помеченном «свой» (С17).
5. **Честный статус.** «Молчит» не выдаётся за «работает», перезапуск не выдаётся за успех.

## 5. Сценарии

### С12. Агент замолчал
Запуск идёт, но ни один агент отдела не выдал события дольше `stall_mins` (по умолчанию 10; у отдела меняется). Сторож помечает запуск «молчит». Дальше по политике отдела:
- `on_stall = "restart"` (по умолчанию, решение хозяина): сторож один раз сам перезапускает зависший шаг в новой сессии с файлами из папки запуска и сообщает хозяину. Повторное зависание того же шага — всегда «notify».
- `on_stall = "notify"`: хозяину приходит карточка «Отдел X молчит 12 мин: последнее действие — …» с кнопками «Подождать ещё», «Перезапустить шаг», «Остановить». Отдел может выбрать это вместо автоперезапуска, например отделы с внешними действиями.

Шаг, который уже выполнил внешнее действие (отправил письмо, запушил ветку, открыл PR), автоматически не перезапускается: сторож всегда переводит такой запуск в «notify».

Агент, который долго выполняет один тяжёлый инструмент (сборка, тесты), не должен считаться зависшим: тулы с известным временем исполнения считаются активностью, пока процесс инструмента жив.

### С13. Упал сам шлюз
Шлюз перезапущен systemd или вручную. При старте он находит запуски в состоянии «идёт», которые не завершились, и для каждого пишет хозяину одно сообщение со сводкой (не по сообщению на запуск, если их больше трёх). Запуск остаётся «застряла: сервер перезапущен» с кнопкой «запустить заново» (как FR-23), но теперь хозяин **узнаёт** об этом сам.

Если шлюз не поднялся вовсе, сообщить некому. Для этого нужен внешний сторож шлюза (С14).

### С14. Сторож шлюза
Нужен и на VPS, и на десктопе (решение хозяина). Лёгкий отдельный процесс (`agentsflow watch`) раз в минуту проверяет `GET /api/health` шлюза. Если шлюз не отвечает N проверок подряд, сторож шлёт хозяину в Telegram сообщение «шлюз не отвечает с HH:MM» напрямую по токену бота, не через шлюз, и, если процесс жив, но завис, завершает его: поднимает новый уже существующий механизм (на десктопе задача Windows «agentsflow» с `deploy/autostart.ps1`, на VPS systemd с `Restart=on-failure`). Если процесс уже завершился, эти механизмы справляются сами, и сторож только сообщает. Когда шлюз вернулся, пишет «шлюз снова работает, запусков прервано: K».

### С15. Событие из репозитория
Хозяин привязывает к отделу репозиторий и источники событий в `department.toml`. Первые два репозитория: `sbx` (код сервиса BuyShark) и сам `agentsflow`; оба помечены как «свои». Пока поддерживаются:
- упал CI (workflow run со статусом failure) на ветке по маске, например `main`;
- новое issue с меткой `agent`;
- комментарий в PR отдела, начинающийся с `/agent`.

Событие превращается в задачу этого отдела с текстом события во входных данных, риском `internal`. Дубли не создаются: одно и то же падение CI на одном коммите даёт одну задачу. Хозяину приходит обычное уведомление «создана задача из события».

Канал получения: опрос API GitHub через `gh` раз в `poll_secs` (по умолчанию 120). Вебхуки не нужны, пока шлюз не слушает наружу (NFR-1 из 001).

### С16. Правка кода заканчивается PR
Отдел с `worktree = true` уже работает в своей git-worktree на ветке `agentsflow/<task>`, и шлюз возвращает эту ветку в локальный репозиторий хозяина. Для отдела с `delivery = "pr"` добавляется следующий шаг: после одобрения ревьюера шлюз пушит ветку и открывает **черновик** PR с описанием из `result.md`, ссылкой на задачу и сводкой расхода. Ссылка на PR идёт в карточку и хозяину. Мерж, снятие «черновика» и любые комментарии на чужие PR остаются за хозяином (`external`).

### С17. Ответ туда, откуда пришло
Задача, созданная из события или сообщения, отвечает в исходное место: CI-задача оставляет комментарий-итог в PR или issue, задача из Telegram отвечает в Telegram, как сейчас. В репозиториях, помеченных «свой» (`sbx`, `agentsflow`), комментарий-итог публикуется сразу, без «принять» (решение хозяина). В остальных репозиториях он остаётся черновиком до принятия. Сообщения агента при этом режутся до фиксированного формата (итог, ссылка на PR, расход) и не содержат дословного текста внешнего события.

## 6. Функциональные требования

**Присмотр за запуском**
- FR-70. Шлюз считает «молчание» запуска как время с последнего события агента текущего шага (сообщение, размышление, вызов и результат инструмента, запрос разрешения). Пока идёт инструмент, действует более длинный порог `tool_stall_mins` (по умолчанию 30), чтобы долгая сборка не считалась зависанием, а зависшая команда всё же ловилась. Пока запрос разрешения ждёт ответа хозяина, молчания нет.
- FR-71. `stall_mins` и `on_stall` задаются в `[limits]` отдела; `home check` проверяет диапазон (1..=timeout_mins).
- FR-72. Причина остановки получает новое значение `Stalled`; сводка «застряла» показывает, на каком шаге и после какого последнего действия агент замолчал.
- FR-73. Автоперезапуск шага — не чаще одного раза на шаг и учитывается в расходе как обычный ход. Он выключен для шага, после которого уже было внешнее действие (С12).
- FR-74. Заявленное в С12 «молчит» видно на странице и в боте на карточке задачи и в списке отдела, не только в уведомлении.

**Перезапуск и сторож шлюза**
- FR-80. При старте шлюз уже помечает идущие запуски «застряла: сервер перезапущен». Добавляется сообщение хозяину: по одному на запуск, если их не больше трёх, иначе одно сводное (С13).
- FR-81. Новый `GET /api/alive` отвечает без токена только «жив» и номером версии; ничего про агентов и задачи не раскрывает. Существующий `GET /api/health` остаётся под основным токеном: токен меняется при каждом запуске шлюза, поэтому внешний сторож им пользоваться не может.
- FR-82. `agentsflow watch` не зависит от кода шлюза: читает токен бота и список хозяев из той же среды, имеет свой таймаут и не падает от недоступного Telegram (повторяет).
- FR-83. Сторож не перезапускает шлюз чаще, чем раз в 5 минут, и после трёх неудачных попыток только сообщает, дальше молчит до возврата шлюза.

**События и PR**
- FR-90. В `department.toml` добавляется необязательный блок `[source]`: `repo`, список `events`, `branches`, `poll_secs`.
- FR-91. Идемпотентность по ключу события (тип, репозиторий, коммит или номер); ключи хранятся в `.agentsflow/`.
- FR-92. Текст события в брифе помечен как внешний и недоверенный; правила отдела сообщают агенту, что инструкции из такого текста не исполняются.
- FR-93. `delivery = "pr"` включает рабочую копию, ветку, push и черновик PR. Без явного `delivery` поведение отдела не меняется.
- FR-94. Для публикации используется `gh` на машине шлюза; токен GitHub не попадает в бриф и в логи агентов.
- FR-95. Отдел с `delivery = "pr"` не работает с репозиторием, к которому у него нет записи в `[source].repo` или `[delivery].repo`.

## 7. Нефункциональные требования

- NFR-10. Сторож шлюза держит менее 20 МБ памяти и не зависит от Rust-кода шлюза, кроме общего формата конфигурации.
- NFR-11. Опрос GitHub не превышает лимит API: общий бюджет запросов делится между отделами, при исчерпании опрос откладывается и хозяину не пишется (только в лог).
- NFR-12. Парность поверхностей (принцип 8 из 001): настройки присмотра, карточки «молчит» и сводка перезапуска есть и на странице, и в боте.
- NFR-13. Старые `department.toml` без новых блоков читаются без изменений и работают как раньше.

## 8. Вне рамок

- Вебхуки с приёмом из интернета: нарушает NFR-1 из 001, пока шлюз не за обратным прокси.
- Автоматический мерж PR, автоматические комментарии на чужие репозитории без принятия.
- Источники кроме GitHub (GitLab, Jira, Sentry) и чатов кроме Telegram. Архитектуру источников делаем так, чтобы добавить их потом, но не реализуем.
- Самопочинка по результатам CI без отдела: любое событие идёт в отдел и проходит ревью.
- Смена модели, ограничение на токены сторожа: сторож не использует ИИ.

## 9. Риски и честные ограничения

1. **Ложные срабатывания «молчит».** Агент может долго думать без вывода. Смягчение: `stall_mins` по умолчанию 10, активность инструментов считается, автоперезапуск один на шаг и никогда после действия наружу.
2. **Перезапуск шага может испортить файлы.** Новая сессия продолжает с файлов в папке, но частично выполненное действие не откатывается. Смягчение: не чаще одного раза на шаг и не после внешнего действия; отдел может выбрать `notify`.
3. **Внешний текст как вектор внедрения.** Issue или комментарий может содержать инструкции для агента. Смягчение: пометка недоверенного, `internal` риск, guard, публикация только через хозяина. Это снижает риск, но не убирает его: агент с shell остаётся агентом с shell (риск 3 из 001).
4. **Опрос вместо вебхуков даёт задержку до `poll_secs`.** Для CI и issue это допустимо.
5. **Правка собственного кода agentsflow.** Отдел с `delivery = "pr"` на репозитории agentsflow меняет код, на котором сам работает. Смягчение: только черновик PR, никакого автоматического мержа, сборки или перезапуска шлюза из-под отдела.
6. **Комментарий без «принять» в свой репозиторий — внешний канал.** Текст идёт в issue и PR, которые могут читать другие. Смягчение: фиксированный формат без дословных кусков внешнего события (С17), репозиторий должен быть явно помечен «свой».
5. **Сторож на десктопе не переживёт выключение компьютера.** Он защищает от падения процесса, не от выключенной машины. Полноценная защита — VPS (NFR-1).
6. **Сведения о Super-agent вторичные.** Если из самого README выяснится другой принцип работы Watchdog или событийной части, меняем реализацию, а не цели.

## 10. Критерий готовности

На VPS бот работает сутки. За это время: один запуск искусственно подвешен (агент заблокирован), и хозяин получил карточку «молчит» через `stall_mins` с нужными кнопками; процесс шлюза убит `kill -9`, и хозяин получил сообщение от сторожа до и сообщение «снова работает» после; в тестовом репозитории красный CI породил задачу, отдел сделал правку, пришёл черновик PR со ссылкой, а мерж сделал хозяин. Ни разу хозяину не пришлось смотреть логи, чтобы понять, что произошло.

## 11. Решения хозяина (2026-11-08)

1. **Зависание.** По умолчанию один автоперезапуск шага (`on_stall = "restart"`) с сообщением хозяину; отдел может выбрать `notify`. Не после внешнего действия.
2. **Репозитории.** Первыми подключаем `sbx` (BuyShark) и `agentsflow`.
3. **Сторож шлюза.** И на VPS, и на десктопе.
4. **Итоговый комментарий.** Для репозиториев, помеченных «свой», публикуется сразу; для остальных после «принять».

Открытых вопросов нет. Следующий шаг: plan.md и tasks.md.
