# agentsflow

Лёгкий шлюз для команды агентов Claude Code и Codex: каждый участник запускается отдельным CLI-процессом, а события приводятся к одному формату. Оркестратор управляет сценариями (workflow) и почтой между участниками.

```
 участники CLI ── адаптеры ──► Hub (seq, история) ── SSE ──► web: колонки участников и оркестратора
                                   ▲                  ◄── POST /api/prompt, /api/permission, /api/workflow/*
                                   │
                            Workflow-движок (шаги, handoff, циклы ревью)
```

Весь код на Rust, страница — один HTML-файл без сборки и внешних зависимостей.

## Быстрый старт

Нужны Rust (stable), установленные и авторизованные CLI `claude` и `codex`.

```sh
cargo run -p agentsflow-gateway -- serve --cwd path/to/project
```

Сервер печатает одну строку вида `agentsflow: http://127.0.0.1:7878/?token=…`. Откройте её в браузере.

- У каждого участника команды своя колонка с лентой, настройками и полем промпта; справа находится оркестратор. Если колонки не помещаются, контейнер прокручивается по горизонтали.
- Запросы разрешений (запуск команды, запись файла) приходят карточкой с кнопками «Разрешить» / «Отклонить». Диффы показываются до решения.
- Справа оркестратор: выберите workflow, задайте задачу и запустите.

По умолчанию Codex работает в песочнице `read-only` и спрашивает разрешение на каждую запись. Для автономной работы: `--sandbox workspace-write`; чтобы не отвечать вручную — `--yes` (автоматически разрешает всё, используйте осознанно).

## Режимы запуска

| Команда | Что делает |
|---|---|
| `agentsflow serve [--port N] [--cwd DIR] [--team pair\|trio\|FILE] [--allow-bypass] [--workflow FILE]…` | Сервер и веб-страница. `--port 0` — свободный порт. |
| `agentsflow team init [FILE]` / `team check <pair\|trio\|FILE>` / `team show` | Создать конфигурацию, проверить команду или показать пресеты. |
| `agentsflow claude "<prompt>" [--model M] [--cwd DIR] [--yes]` | Один ход Claude, события в консоль, разрешения через `y/N`. |
| `agentsflow codex "<prompt>" [--sandbox read-only\|workspace-write] [--codex-bin PATH] …` | То же для Codex. |
| `agentsflow flow <file.toml> --task "<text>" --yes [опции]` | Headless-запуск workflow. `--yes` обязателен: отвечать на разрешения некому. Код выхода 0 — workflow завершён, 1 — провален, 2 — ошибка аргументов. |

Общие опции: `--cwd`, `--claude-model`, `--codex-model` (для `serve`/`flow`), `--sandbox`, `--codex-bin`. Бинарь `codex` ищется так: `--codex-bin`, переменная `CODEX_BIN`, установленное приложение (Windows), затем `PATH`.

## Команда агентов

По умолчанию используется `pair`: участники `claude` и `codex`. Пресет `trio` содержит `lead` (Claude Sonnet 5.5, high), `main` (Terra, medium) и `junior` (Terra, low). Для трёх участников рекомендуется `agentsflow serve --team trio --mail-thread-limit 40`.

`agentsflow team init [FILE]` создаёт шаблон `team.toml`, не перезаписывая файл. `agentsflow team check FILE` проверяет его и показывает таблицу; `agentsflow team show` показывает пресеты. Пример своего файла:

```toml
[[agent]]
id = "lead"
kind = "claude"
model = "claude-sonnet-5-5"
effort = "high"
title = "лидер и ревьюер"
roles = ["lead", "reviewer"]
lead = true

[[agent]]
id = "main"
kind = "codex"
roles = ["engineer"]
```

Запуск: `agentsflow serve --team team.toml`. Допустимы 1–6 участников и ровно один лидер; ID состоят из строчных латинских букв, цифр, `_` и `-`. В почте участники адресуются по ID, в workflow — по ID или роли. Старый `--agents claude,codex` фильтрует `pair` и несовместим с `--team`. Модель из настроек участника имеет приоритет над общим флагом модели.

Режим доступа задаётся отдельно для каждого участника:

| Поле | Значения и наследование |
|---|---|
| `mode` | `ask` — спрашивать разрешения; `auto` — разрешать автоматически; `bypass` — обход разрешений и песочницы Codex. Если поле не задано, используется `auto` при `--yes`, иначе `ask`. |
| `sandbox` | Только для Codex: `read-only` или `workspace-write`. Без поля наследуется `--sandbox`, иначе используется `read-only`. В `bypass` поле запрещено. |

В пресете `trio` участники `main` и `junior` используют `workspace-write` и наследуют режим. Для bypass нужно явно подтвердить запуск флагом `--allow-bypass` у `serve` или `flow`; `team check` выводит предупреждение. **Bypass снимает проверки разрешений, а у Codex также песочницу:** используйте его только когда доверяете задаче и окружению. Пример участника без песочницы:

```toml
[[agent]]
id = "worker"
kind = "codex"
lead = true
mode = "bypass"
```

Запуск: `agentsflow serve --team team.toml --allow-bypass`. Глобальный `--sandbox` не принимает `danger-full-access`.

Веб-страница получает состав команды из `/api/state` и показывает колонки в порядке конфигурации. События из старых журналов для неизвестных ID отображаются в отдельных нейтральных колонках.

## Единый формат событий

Каждое событие — `Envelope { session, agent, seq, ts_ms, event }`, где `agent` — ID участника или `orchestrator`. Варианты `event` (поле `type`):

`message` · `tool_call` · `tool_result` · `diff` · `permission_request` · `permission_resolved` · `done` · `error` · `handoff` · `workflow`

Диффы Codex приходят из его `fileChange`; для Claude патч синтезируется из `Write`/`Edit`/`MultiEdit` и показывается раньше запроса разрешения.

При запуске `serve --log FILE` события дописываются в JSONL-файл; после перезапуска восстанавливаются последние 5000 событий. Всё, что прошлый запуск не успел закончить (запрос разрешения, ход агента, workflow), закрывается событиями с пометкой `interrupted: server restarted`, чтобы страница не показывала мёртвые карточки.

## Экспорт сессии

Кнопки «Экспорт» скачивают текущую историю в Markdown или JSONL.
Маршрут `GET /api/export?format=md|jsonl` по умолчанию возвращает Markdown.
Экспорт доступен только с основным токеном; личные токены агентов не подходят.

## HTTP API

Все `/api/*` требуют токен: query `?token=…` или заголовок `x-agentsflow-token`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/events` | SSE: сначала вся история (до 5000 событий), затем новые. `id` = `seq`. |
| `POST /api/prompt` `{agent, text}` | Промпт агенту. 202 / 409 (занят) / 404 / 400. |
| `POST /api/agent/interrupt` `{agent}` | Прервать текущий ход участника. 200 / 404 / 409 (не занят); только основной токен. |
| `POST /api/permission` `{agent, id, allow}` | Ответ на запрос разрешения. |
| `GET /api/state` | Рабочая папка, состояние агентов, текущий workflow. |
| `GET /api/team` | Участники команды в порядке конфигурации. |
| `GET /api/workflows` | Список доступных workflow. |
| `POST /api/workflow/run` `{name, task}` | Запуск. 202 / 404 / 400 / 409 (уже идёт). |
| `POST /api/workflow/stop` | Остановка между шагами. Текущий ход агента прервать нельзя, он просто не ожидается. |

Безопасность: сервер слушает только `127.0.0.1`, проверяет заголовок `Host` (защита от DNS rebinding) и `Origin` у POST, токен генерируется при каждом запуске. Страница может одобрять выполнение команд, поэтому не пробрасывайте порт наружу.

## Остановка хода

Кнопка «Стоп» в колонке участника прерывает его текущий ход, сохраняя сессию для следующего промпта.
Маршрут `POST /api/agent/interrupt` принимает `{agent}` и возвращает 200 при успехе, 404 для неизвестного участника и 409 `not busy`, если он свободен.
Маршрут доступен только с основным токеном; личный токен агента получает 403.
Ожидающие разрешения отклоняются, а ход завершается событием `done` с причиной `interrupted`.
Ожидающий этот ход шаг workflow завершается ошибкой `interrupted`; почтовые шаги не затрагиваются.

## Защита от разрушительных команд (guard)

Guard проверяет текст команды в запросах разрешения инструментов оболочки. По умолчанию он включён у каждого участника; `guard = false` в его блоке `[[agent]]` отключает проверку. В `auto` опасная команда отклоняется автоматически, в `ask` карточка показывает предупреждение и решение принимает человек. В `bypass` запросы разрешений обходятся, поэтому guard не работает. При автоматическом отказе Claude получает причину; протокол ответа Codex передаёт только отказ.

| Правило | Примеры |
|---|---|
| `rm-recursive` | Рекурсивное удаление корня проекта, `.git` или пути вне разрешённых каталогов. Разрешены подпапки проекта и временные каталоги. |
| `git-reset-hard`, `git-clean`, `git-force-push`, `git-discard` | Потеря изменений, переписывание истории или удаление ссылок Git. |
| `disk` | Форматирование и перезапись диска. |
| `sql` | Разрушительные SQL-команды, переданные клиенту базы. |
| `perm` | Рекурсивное изменение прав корня файловой системы. |

Проверка приблизительно разбирает команды и известные обёртки, не запускает процессы и не является песочницей. Сложные конструкции, обфускация, неизвестные обёртки и действия вне оболочки могут остаться незамеченными; неразобранное не блокируется. Пути проверяются лексически, без разрешения символических ссылок. Предупреждение видно на карточке разрешения и в Markdown-экспорте.

## Telegram

Создайте бота через @BotFather и задайте его токен только в переменной окружения `AGENTSFLOW_TELEGRAM_TOKEN`. В `AGENTSFLOW_TELEGRAM_USERS` перечислите через запятую числовые ID пользователей, которым доверяете; свой ID можно узнать у @userinfobot. Запустите `agentsflow serve --telegram`. Необязательный `AGENTSFLOW_TELEGRAM_API` меняет адрес Bot API для тестирования.

Мост показывает команду и состояние агентов, присылает запросы разрешений с кнопками, результаты workflow, письма оркестратору, сданные на проверку и застрявшие задачи, ошибки и завершения длительных ходов. Опасные команды требуют отдельного подтверждения, BYPASS - подтверждения перед первым заданием.

Telegram может отправлять задания агентам и отвечать на запросы разрешений. **Взлом аккаунта Telegram владельца означает возможность управления его компьютером.** Доверяйте доступ только тем, кому готовы разрешить такие действия; рекомендуется двухфакторная авторизация Telegram. Чтобы отключить отправку заданий, задайте `AGENTSFLOW_TELEGRAM_PROMPTS=0`. Доступ ограничен белым списком, токен не передаётся аргументом запуска.

Всё, что есть на странице, доступно и в боте, под теми же названиями. Внизу чата постоянные кнопки «Команда», «Запросы», «Доска», «Почта», «Ещё».

| Возможность | Страница | Telegram |
|---|---|---|
| Состояние команды и агента | «Обзор», чаты | «Команда» → агент, `/team`, `/status`, `/agent <имя>` |
| Задание агенту | Поле ввода в колонке | «Написать», `/ask <имя> <текст>` |
| Остановка хода | «Стоп» | ⏹ на карточке агента, `/stop <имя>` |
| Разрешения и опасные команды | Карточка в «Ждёт вас» | Уведомление с кнопками, «Запросы», `/requests` |
| Доска: список по колонкам | «Доска» | «Доска», `/board`: вкладки статусов со счётчиками и страницами |
| Создать задачу | «Новая карточка» | «＋ Новая задача» или `/task <название> \| <описание>` |
| Карточка: статус, исполнитель, название, описание | Поля карточки | Кнопки «Статус», «Исполнитель», «Название», «Описание» |
| Запустить, принять, вернуть, в архив | Кнопки карточки | Те же кнопки; принять и архив спрашивают подтверждение |
| Перетаскивание карточки | Мышью | Нет: вместо него меню «Статус» |
| Почта: список, переписка, ответ, новое письмо | «Почта» | «Почта», `/mail`, `/mail <агент> <тема> \| <текст>` |
| Запуск и остановка workflow | «Workflow» | «Ещё» → «Запуск workflow», `/run`; ⏹ в живом сообщении |
| Статистика | «Статистика» | «Ещё» → «Статистика», `/stats` |
| Что делал агент | Журнал в колонке | «Ещё» → «Что делал агент», `/log <имя> [n]` |
| Экспорт | Кнопка экспорта | «Ещё» → «Экспорт», `/export md\|jsonl`; файл уходит через серверы Telegram, поэтому бот просит подтвердить один раз |
| Тишина | Нет | `/mute`, `/unmute`, «Ещё» |
| Токен страницы и ссылка доступа | Адрес в консоли | Нет: ссылка остаётся на компьютере |

Полный список команд: `/team`, `/requests`, `/board`, `/task`, `/mail`, `/ask`, `/agent`, `/stop`, `/run`, `/stats`, `/log`, `/export`, `/mute`, `/unmute`, `/status`, `/more`, `/help`. Тест проверяет, что каждая команда из меню бота действительно обрабатывается. Экран «Ещё» собирает статистику, запуск workflow, историю агента, экспорт, тишину и справку. Время в сообщениях - UTC.

Сообщения проходят через серверы Telegram и не имеют сквозного шифрования. В них могут попасть команды агентов и части писем; не включайте мост, если в командах или диффах есть секреты.

## Задачи (доска)

Карточка содержит заголовок, описание, исполнителя, прогресс, метки, примечание, почтовый тред и время создания/изменения. Статусы: `backlog`, `todo`, `in_progress`, `review`, `done`, `blocked`, `archived`. В журнале `--log` сохраняется полный снимок после каждого изменения; при восстановлении побеждает последний снимок в истории. Максимум 500 неархивных карточек.

| API | Назначение |
|---|---|
| `GET /api/tasks?include_archived=0\|1` | Список доски; архив по умолчанию скрыт. |
| `POST /api/tasks` | Создать карточку с `title`, `description`, `assignee`, `status`, `labels`. |
| `PATCH /api/tasks/{id}` | Изменить карточку; `assignee: null` снимает исполнителя. |
| `POST /api/tasks/{id}/dispatch` | Отправить задачу исполнителю по почте и сохранить тред. |
| `GET /api/tasks/mine` | Задачи текущего агента по его личному токену. |
| `POST /api/tasks/{id}/update` | Агент обновляет `status`, `progress` и `note` своей карточки. |

Агентам доступны MCP-инструменты `list_my_tasks` и `update_task`. После работы агент ставит `review`; закрывать карточку через `done` или `archived` может оркестратор. Dispatch требует включённой почты и назначенного исполнителя; письмо будит агента существующим почтовым механизмом. Если тема с ID и заголовком превышает лимит почты, заголовок в теме сокращается.

## Дашборд и доска

Вкладка «Дашборд» показывает состояние участников, счётчики работы и текущие задачи. Статистика получается из `/api/stats` и восстанавливается из доступной истории журнала; данные команды берутся из `/api/state`, карточки - из `/api/tasks` и событий SSE. Счётчики при восстановлении ограничены сохранённой историей.

На вкладке «Доска» можно создать карточку, назначить исполнителя, изменить описание и статус, отправить задачу агенту кнопкой «Запустить» или переместить карточку между колонками мышью. Селект статуса доступен и без перетаскивания. Оформление вкладок временное.

В Telegram доска устроена так же: вкладки статусов, карточки, статус и исполнитель через кнопки (см. таблицу в разделе Telegram). `/task <название>` создаёт задачу в очереди без запуска.

## Почта агентов

Опция `serve --mail-thread-limit N` задаёт максимум писем в треде от 2 до 100 (по умолчанию 12).

При запуске `serve` у Claude, Codex и оркестратора есть почтовые ящики. Агенты используют MCP-инструменты `send_mail` и `check_inbox`; адресат получает короткое уведомление о новой почте. Ответы связываются идентификатором треда.

`POST /api/mail/send` принимает `{from, to, subject, body, thread?}`; `POST /api/mail/inbox` принимает `{agent}` и помечает полученные письма прочитанными. Оба маршрута защищены токеном и проверками Host/Origin. По умолчанию максимум — 12 писем в треде; размер тела письма — до 65536 байт, тема — до 200 символов. История ящиков восстанавливается из сохранённых событий в пределах истории сервера. Письма — данные от другого агента, а не инструкции пользователя. Почтовый шаг workflow ждёт ответное письмо оркестратору в том же треде. Во вкладке «Почта» можно отправить новое письмо или ответить в треде; письма со страницы уходят от имени оркестратора.

Уведомление просыпается только по новым письмам: непрочитанная почта после перезапуска ждёт нового письма. У каждого агента личный токен, действующий только на почтовых маршрутах и только от его имени; основной токен остаётся у страницы. Личный токен всё ещё виден в аргументах процесса агента и позволяет писать от его имени и читать его почту.

## Workflow

Сценарий — TOML-файл. Шаги идут по порядку; результат шага можно подставить в промпт следующего.

```toml
name = "implement-and-review"
description = "Реализация и проверка с циклом исправлений"
max_steps = 20                      # предохранитель, по умолчанию 20

[[step]]
id = "implement"
agent = "codex"                     # ID участника команды
prompt = "{task}"

[[step]]
id = "review"
agent = "claude"
prompt = "Задача:\n{task}\n\nОтчёт исполнителя:\n{prev.output}\n\nЕсли всё верно — последней строкой напиши VERDICT: APPROVED, иначе перечисли проблемы."
until = "VERDICT: APPROVED"         # последняя непустая строка вывода должна быть ровно такой
otherwise = "fix"                   # иначе перейти на шаг fix…
max_loops = 2                       # …не более 2 раз (по умолчанию 2), затем workflow Failed
next = "end"                        # при успехе завершить

[[step]]
id = "fix"
agent = "codex"
prompt = "Замечания ревьюера:\n{review.output}\n\nИсправь их."
next = "review"
```

- В `agent` и `cc` можно указать `@role`: выбирается первый участник с этим тегом, а `@lead` всегда выбирает лидера. В `cc` значение `@others` добавляет остальных участников. Буквальные ID тоже поддерживаются.
- Плейсхолдеры: `{task}`, `{<id>.output}`, `{prev.output}`, `{team}` (список участников с ролями) и `{@role}` (ID участника роли). Неизвестные роли и повторы получателей выявляются при запуске.
- Выводом шага считается последнее сообщение агента за ход.
- `until` проверяет не подстроку, а вердикт: он засчитывается, только если это вся последняя непустая строка вывода (пробелы и markdown-выделение вокруг игнорируются). «NOT VERDICT: APPROVED» или вердикт, за которым идут замечания, не проходят. Берите редкий маркер, который ревьюер не станет писать в замечаниях.
- Когда промпт строится из чужого вывода, оркестратор публикует `handoff { from, to, step, text }`: на странице это карточка «claude → codex» и пометка «← claude · fix» у промпта в колонке получателя.
- Ошибки спецификации (дубликаты id, неизвестные шаги и плейсхолдеры, `otherwise` без `until`, неизвестные ключи) ловятся при загрузке.
- При запуске проверяется, что все `agent` и `cc` входят в текущую команду.
- Встроены `implement-and-review`, `cross-check`, `mail-review` и `mail-team`; свои файлы подключаются `serve --workflow FILE` (можно несколько раз). Для `pair` инженер — `codex`, ревьюер и лидер — `claude`; для `trio` инженер — `main`, ревьюер и лидер — `lead`, а `junior` участвует в `mail-team`.
- Для `mode = "mail"` оркестратор отправляет `prompt` письмом указанному `agent` и ждёт ответа себе в том же треде; тело ответа становится выводом шага. Почта доступна только при запуске через `serve`.
- Необязательный `subject` задаёт тему письма (по умолчанию id шага), `timeout_secs` — время ожидания ответа (по умолчанию 900 секунд, диапазон 1–7200). `until` проверяет последнюю строку ответа, как и у обычного шага.
- Пример `workflows/mail-review.toml`: Codex реализует задачу, самостоятельно переписывается с Claude в одном треде и присылает оркестратору итог с вердиктом.
- В почтовом шаге `cc = ["claude"]` отправляет копию того же письма дополнительному агенту в общем треде; эти письма учитываются в лимите треда.
- `mail-team`: лидер и остальные участники делят файлы по почте, работают и проводят ревью в общем треде; лидер присылает итог с `VERDICT: APPROVED`. Для трёх участников рекомендуется `serve --mail-thread-limit 40`.
- Одновременно выполняется один workflow.

## Разработка

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p agentsflow-adapters -- --ignored   # живые тесты, нужны claude и codex
```

CI (GitHub Actions) выполняет те же проверки на Linux и Windows и проверяет синтаксис скрипта страницы.

Структура:
- `crates/events` — формат событий (`Envelope`, `Event`).
- `crates/adapters` — трейт `Agent`; `claude` (на `claude-codes`) и `codex` (на `codex-codes`).
- `crates/gateway` — `hub` (шина событий и актор на агента), `server` (axum), `workflow` (движок), `runtime`, `cli`.
- `web/index.html` — интерфейс. `workflows/` — встроенные сценарии.

## Ограничения

- Протоколы CLI нестабильны: крейты привязаны к версиям `claude` 2.1.x и `codex` 0.16x.
- Сообщения приходят целиком, без токенового стриминга.
- Одна рабочая папка и по одной долгоживущей сессии на агента.
